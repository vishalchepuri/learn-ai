Text Embedding Algorithms

An embedding turns a word or sentence into a list of numbers (a vector). Words that mean similar things get similar numbers. That's how computers understand language — not by reading words, but by comparing number patterns.

What does a word look like as numbers?

Example 1
Imagine giving every word a coordinate in a 3D space:

Axis 1 — Royalty: how "royal" the word is (king=high, dog=low)
Axis 2 — Maleness: how masculine the word is (man=high, woman=low)
Axis 3 — Animal: how animal-like the word is (dog=high, king=low)

Real embeddings have 768–4096 axes — we use 3 here to make it visible. Click a word below to see its numbers:
Click any word above to see its vector.

Similar words = similar numbers

Example 2
Two words are "similar" when their vectors point in the same direction. We measure this with cosine similarity (0% = totally different, 100% = identical).

Try comparing: king vs queen (both royal → should be similar), then king vs dog (very different).
Select two words and compare.

word2vec Magic: king − man + woman = queen

Example 3
The most famous example in all of NLP. Here's the intuition:

1 king − man = removes the "maleness" from king, leaves only "royalty"
2 + woman = adds "femaleness" to that royalty vector
3 Find nearest word to the result — and it's queen!

This works because word2vec learned these directions from reading millions of sentences.
Click to see the step-by-step arithmetic.

BERT vs ColBERT — one vector vs many vectors

Example 4
BERT reads a whole sentence and squishes it into one single vector. The problem: the word "bank" (river bank vs. financial bank) gets the same treatment — detail is lost.

ColBERT keeps one vector per word/token. When searching, each query word matches the best document word separately. Much more precise — especially for multi-word queries.

Vector Similarity — Cosine, Dot Product, Euclidean

Once you have two vectors, you need a formula to measure how similar they are. Three common formulas exist — each one asks a different question about the vectors. Using the wrong one quietly hurts your retrieval quality.

Live similarity calculator — see all three formulas

Example 1
Enter any two vectors (same number of values, comma-separated) and see all three metrics calculated with the formula shown step by step.

Try this: A = 1, 0, 0 and B = 1, 0, 0 (identical) — cosine = 1.0
Then try: A = 1, 0, 0 and B = 0, 1, 0 (perpendicular) — cosine = 0.0
Enter vectors and calculate.

When to use each metric

Example 2
Cosine Similarity — asks "do these vectors point in the same direction?"
It ignores the length (magnitude) of the vectors. Two sentences about "dogs" will point in the same direction whether the text is short or long.

Dot Product — asks "same direction AND how strong?"
A longer sentence might have a bigger vector, so it scores higher even for the same topic. Only use this if your vectors are unit-normalized (length = 1).

Euclidean Distance — asks "how far apart are these points in space?"
Works well for low-dimensional data (GPS, images). Breaks down for high-dimensional text embeddings (curse of dimensionality).

HNSW Index — Fast Approximate Nearest Neighbour Search

You have 10 million document embeddings. To find the most similar one to your query, brute force would compare all 10 million — that takes seconds. HNSW finds nearly the same answer in under 10 milliseconds by building a smart graph.

Why do we need a special index?

Example 1
Brute force search:
Compare query to every document → 10M comparisons × 1536 multiplications = billions of operations per query.

HNSW (Approximate Nearest Neighbour):
Build a graph once at index time. At query time, navigate the graph — visit only ~100–200 nodes instead of millions.

Trade-off: you get ~99% of the right answers at 1000× the speed. That 1% miss is acceptable for search.
1You upload 10M documents → each gets embedded → stored in HNSW graph
2User asks a question → question gets embedded → query vector
3HNSW navigates the graph, visits ~150 nodes (not 10M), finds nearest
4Returns top-k most similar documents in <10ms

HNSW search — tune M and ef_search

Example 2
M = how many neighbours each node connects to in the graph. Higher M = better connections = better recall, but more memory and slower build.

ef_search = how many candidate nodes to explore during a query. Higher = more accurate, but slower. You can tune this without rebuilding the index.
Set parameters and run a search.

The "Hierarchical" part — how layers work

Example 3
HNSW builds multiple layers — like a city with highways, main roads, and side streets.

Top layer: Very few nodes, long connections → lets you jump far quickly
Middle layers: More nodes, medium connections → narrow down to the right area
Bottom layer (0): All nodes, short connections → precise local search

Search starts at the top (fast rough navigation) and drills down to the bottom (precise result).

Chunking Strategies for RAG

Raw documents are too big for embeddings. Split them into smart chunks: not too small (lose context) or too big (dilute relevance). Wrong chunking is the #1 hidden cause of RAG failures.

Key topics (tap to expand)

★ Fixed Size Chunking: Simple 512-token chunks, causes context breaks
★ Recursive Chunking: Split on paragraph, sentence, word — preserve meaning
★ Semantic Chunking: Use embeddings to find natural boundaries
★ Sliding Window: Overlapping chunks (50% overlap prevents info loss)
★ Parent-Child Chunks: Small chunks for search, large chunks for context

All concepts

› Chunk size: 256-512 tokens optimal (too small = lose context, too big = dilute relevance)
› Overlap: 20-50 tokens (prevents cutting answers in half)
› Fixed size: Fast, simple, loses document structure
› Recursive: Langchain default, respects paragraphs → sentences → words
› Semantic: Run embeddings on chunks, merge low-similarity neighbors
› Sliding window: token_start = 0; next = current + 256 - 50 overlap
› Parent-child: Index small chunks (256T), retrieve context from parent (1024T)
› Metadata: Keep doc_id, page_number, section headers in chunk metadata

Hybrid Search (Keyword + Vector)

Vector search alone misses exact matches and acronyms. Combine keyword search (BM25) with vector search, rank results with RRF (Reciprocal Rank Fusion), get the best of both worlds.

Key topics (tap to expand)

★ BM25: TF-IDF based keyword search, fast, matches exact phrases
★ Vector Search: Semantic matching across topics and paraphrasing
★ Reciprocal Rank Fusion (RRF): Combine rankings without comparing scores

All concepts

› BM25 algorithm: Term frequency, inverse document frequency, saturation
› Vector search limitations: Misses exact phrases, acronyms, numbers
› Hybrid search benefits: 15-20% better precision than either alone
› RRF formula: score = 1/(rank+60) — rank aggregation without comparing scores
› Implementation: Weaviate, Elasticsearch, Pinecone hybrid
› Weighting strategies: 70% vector + 30% BM25 vs dynamic weights
› Real-world gains: Legal docs (+25% precision), product catalogues (+18%)

D1 — Embeddings + Vector Databases

Quantization (Compress Vectors)

Full-precision embeddings (768 float32 = 3KB per vector) are expensive. Quantize to 8-bit integers (1/4 the size), keep 97% of quality. Trade 3% accuracy for 4x cheaper storage and faster search.

Key topics (tap to expand)

★ Product Quantization (PQ): Divide vector into subspaces, quantize each
★ Scalar Quantization: Round to fewer bits (float32 → int8)
★ Binary Quantization: Vectors as single bits (96% space savings)

All concepts

› float32: 768 dims × 4 bytes = 3KB per vector
› int8: 768 dims × 1 byte = 768 bytes per vector (75% savings)
› Binary: 768 dims ÷ 8 = 96 bytes (96% savings, recall loss ~5%)
› Product Quantization: Split 768D → 8 × 96D subquantizers
› Tradeoffs: Size vs accuracy vs speed
› Benchmarks: 1M vectors: 3GB (float32) vs 750MB (int8) vs 96MB (binary)
› When to quantize: Static knowledge bases, not real-time learning

RAG vs Fine-tuning Decision Framework

Have domain data? Two paths: RAG (retrieve external docs) or fine-tune (bake knowledge into weights). Costs, latency, and flexibility are very different.

Key topics (tap to expand)

★ RAG: Retrieve current docs, 100ms latency, $0.001/query
★ Fine-tune: Bake knowledge in model, instant (no retrieval), requires training
★ Hybrid: Fine-tune + RAG for maximum quality

All concepts

› When to RAG: Knowledge changes monthly, budget-conscious, need explanations
› When to fine-tune: Stable knowledge base, formatting critical, high volume
› When to hybrid: Knowledge half-changes, zero tolerance for errors
› RAG costs: Token costs for LLM only
› Fine-tune costs: GPU compute + inference (model serving)
› Latency: RAG ~150-500ms (retrieval + generation), FT ~300ms (inference only)
› Data requirements: RAG needs 0 examples, FT needs 100-1000
› Eval metrics: Accuracy, latency, cost per query, knowledge freshness

Advanced Retrieval Techniques

Basic vector search misses questions phrased differently. Use HyDE (generate hypothetical answers), Multi-query (rewrite questions), Step-back (go abstract), or Reranking to find the right documents.

Key topics (tap to expand)

★ HyDE: Generate fake answer, search for it
★ Multi-query: Rewrite question 5 ways, search all
★ Step-back: Generalize question, retrieve broader context
★ Reranking: Re-score top-100 with expensive model

All concepts

› HyDE (Hypothetical Document Embeddings): User query → Generate answer → Use answer embedding to search
› Multi-query: "What's the fastest GPU?" → Rewrites: "GPUs by speed", "GPU benchmarks"
› Step-back: "How to fine-tune BERT on medical text?" → Generalizes to "Fine-tuning transformer models"
› Reranking: Top-100 from vector search → Cross-encoder re-scores → Top-10 final
› Latency impact: +50-200ms per technique
› Recall improvement: +5-15% with HyDE, +10-20% with multi-query
› Combining: HyDE + Multi-query + Reranking = 25-30% better recall

D3 — Advanced RAG + Evaluation

RAGAS Evaluation Framework

How good is your RAG system? RAGAS measures Faithfulness (not hallucinating), Context Relevance (retrieving right docs), Answer Relevance (answering the question), and Ground Truth if you have it.

Key topics (tap to expand)

★ Faithfulness: Is answer grounded in context? (0-1 score)
★ Context Relevance: Is retrieved context useful? (0-1 score)
★ Answer Relevance: Does answer address question? (0-1 score)
★ Aspect Ratio: Combined metric across all three

All concepts

› Faithfulness (0.0-1.0): Given context, is answer factually correct?
› Context Relevance (0.0-1.0): Do top-5 docs actually help answer question?
› Answer Relevance (0.0-1.0): Does output answer the input question?
› Aspect Ratio: Harmonic mean of the three
› Ground Truth comparison: If you have gold answers, measure exact/semantic match
› Running RAGAS: 2-3 seconds per (question, context, answer) triple
› Thresholds: >0.8 is good, >0.9 is excellent, <0.5 needs rework
› Dataset: Evaluate on 50+ diverse questions for confidence

Agentic RAG (Self-Correcting)

Basic RAG returns wrong answer once. Agentic RAG detects "I don't know the answer" and re-retrieves. Add self-reflection: "Is this answer good?" Loop until confident.

Key topics (tap to expand)

All concepts

› Self-RAG: Generate answer → Critique answer → If bad, retrieve more docs
› Adaptive: Ask "Do I need to search?" before each retrieval
› Iterative: "What's the CEO's favorite food?" → Sub-question 1: CEO name, Sub-q 2: favorite food

› Implementation: ReAct (Reasoning + Acting), Tool use
› Latency: 2-3x slower than single-pass RAG (300-500ms vs 1-2s)
› Accuracy gain: +10-20% for complex questions

Hallucination Detection & Mitigation

Even state-of-the-art models hallucinate (invent facts). Detect with NLI (Natural Language Inference), prevent with constrained decoding, mitigate by requiring citations.

Key topics (tap to expand)

★ NLI-based Detection: Entailment between context and answer
★ Self-Consistency: Multiple generations → vote on answer
★ Citation-based: Force model to quote sources
★ Constrained Decoding: Only generate tokens from retrieved docs

All concepts

› NLI check: Answer must be entailed by context (contradiction score < 0.3)
› Self-consistency: Generate answer 5 ways, aggregate with majority vote
› Citation forcing: "According to document X, the answer is..."
› Constrained tokens: Use token IDs from context only
› Hallucination rates: GPT-4 ~5%, Claude ~3%, Llama ~8% on RAG
› Zero hallucination: Trade accuracy for safety (avoid weak answers)
› Monitoring: Track "unsupported claims" in production

3 Types of Hallucination

1Extrinsic: Facts not in documents
2Intrinsic: Self-contradiction
3Logic: Invalid reasoning

D6 — Fine-tuning + PEFT

LoRA Deep Dive (Low-Rank Adaptation)

Fine-tune a 7B model by training only 0.1% of parameters. Instead of tuning 7B params, add two small matrices A (7B×8) and B (8×out), train only those. Result: 10x cheaper, same quality.

Key topics (tap to expand)

★ LoRA Mathematics: Low-rank decomposition of weight updates
★ QLoRA: Quantization + LoRA (4-bit quantization + LoRA)
★ Efficiency: Train on single GPU instead of 8
★ Merging: Merge LoRA weights back into base model

All concepts

› Low-rank assumption: Weight updates lie in low-dimensional space
› Matrices A, B: 7B×rank (usually rank=8), rank×out
› Rank selection: rank=4 for efficiency, rank=16+ for quality
› QLoRA: Quantize base model to 4-bit NF4, add LoRA
› PEFT library: AutoPEFTModelForCausalLM, LoraConfig
› Memory: 7B model (28GB FP32) → 7B int4 (2GB) + LoRA (64MB)
› Speed: Training 1.5-2x slower than inference
› Merging: Option to keep separate (adapter) or merge (single file)

D1 — Embeddings + Vector Databases

ColBERT — Late Interaction Retrieval

Single-vector embeddings (BERT) compress an entire document into one vector — losing detail. ColBERT keeps one vector per token and matches them late at query time. Result: dramatically better precision on multi-word queries.

Key topics (tap to expand)

★ Single-vector (BERT): 1 doc = 1 vector (768 floats)
★ Multi-vector (ColBERT): 1 doc = N vectors (1 per token)
★ MaxSim operator: For each query token, find max-similarity doc token
★ Late interaction: Match at query time, not encode time

All concepts

› Standard BERT pooling: Mean/CLS pooling kills word-level detail
› ColBERT v1: Stores all token vectors per doc (~100KB/doc)
› ColBERT v2: Centroid + residual quantization (~10KB/doc)
› MaxSim: sum_q max_d cos(q_i, d_j) — every query word finds best doc word
› Storage cost: 100x larger than single-vector (mitigated in v2)
› Quality gain: +5-15% nDCG over BERT on retrieval benchmarks
› Tools: RAGatouille (Python), ColBERTv2 checkpoint
› Use when: Long technical queries, exact phrase matters

You fine-tuned a model. Now serve it. Ollama for local desktop & dev (one command). vLLM for production GPU servers (high throughput with PagedAttention). Different tools for different stages.

Key topics (tap to expand)

★ Ollama: Local LLM runner, GGUF format, OpenAI-compatible API
★ vLLM: GPU inference server, PagedAttention, continuous batching
★ GGUF: Quantized format for CPU/Apple Silicon
★ Serving fine-tuned: Merge LoRA → convert → deploy

All concepts

› Ollama setup: brew install ollama; ollama pull llama3
› Modelfile: Define system prompt, temperature, custom model
› GGUF quantization: Q4_K_M (balanced), Q5_K_M (better), Q8_0 (best)
› vLLM features: PagedAttention, continuous batching, prefix caching
› Throughput: vLLM 10-30x higher than naive HF generate
› OpenAI-compatible: Both expose /v1/chat/completions
› LoRA in vLLM: --enable-lora → swap adapters per request
› When Ollama: Dev, demos, single user. When vLLM: prod, many users
